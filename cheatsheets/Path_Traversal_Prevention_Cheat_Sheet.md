# Path Traversal Prevention Cheat Sheet

## Introduction

Path traversal happens when an application builds a file system path from user input and the input can make that path point outside the directory the application meant to use. Sequences such as `../`, absolute paths, or symbolic links let an attacker read, write or include files such as configuration, credentials or source code ([CWE-22](https://cwe.mitre.org/data/definitions/22.html)).

This cheat sheet covers how to build file paths from untrusted input safely. For storing uploaded files, see the [File Upload Cheat Sheet](File_Upload_Cheat_Sheet.md). For testing, see [WSTG-ATHZ-01 Testing Directory Traversal File Include](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/05-Authorization_Testing/01-Testing_Directory_Traversal_File_Include/).

## Avoid User Input in File Paths

The most reliable defense is to never put user input into a path:

- Refer to files by an identifier, such as a database ID or a random name generated by the server, and map it to the real path on the server side.
- If the user picks from a fixed set of files or templates, look the name up in an allowlist and use the stored path, not the input.
- Store user content where paths don't matter, such as a database or object storage keyed by an ID.

When the application has to accept a name from the user, also restrict it to a simple allowlist of characters, for example letters, digits, `-` and `_`, with no path separators. This is an extra layer, not a replacement for the containment check below, because a character filter can't account for every way an operating system interprets a path ([CWE-22](https://cwe.mitre.org/data/definitions/22.html)).

## Validate the Resolved Path

If the input has to become part of a path, resolve the full path first and then check that the result is still inside the intended base directory:

1. Decode the input completely (URL decoding, Unicode normalization) before using it, and don't decode it again afterwards.
2. Join it to a fixed base directory and resolve it to an absolute, normalized path. Resolve symbolic links as well where the platform allows it.
3. Check that the resolved path is inside the base directory. Compare path components, or compare strings only after making sure the base ends with a path separator, so `/srv/uploads-old` doesn't pass a check for `/srv/uploads`.
4. Use the path you checked. Don't rebuild it from the original input.

Don't try to remove `../` from the input instead. A filter misses `\` on systems that also accept it as a separator, can leave a `../` behind when it only removes one occurrence, is bypassed by input that gets decoded after the check (such as `%2e%2e%2f`), and does nothing about absolute paths ([CWE-22](https://cwe.mitre.org/data/definitions/22.html)).

Many join functions drop the base directory when the second argument is absolute. Python's `os.path.join('/srv/uploads', '/etc/passwd')` returns `/etc/passwd` ([Python `os.path.join`](https://docs.python.org/3/library/os.path.html#os.path.join)), .NET's `Path.Combine` returns the second path if it's absolute ([.NET `Path.Combine`](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.combine)), and Node's `path.resolve` starts over at the last absolute segment ([Node.js `path.resolve`](https://nodejs.org/api/path.html#pathresolvepaths)). The containment check after resolving catches this.

The examples below are minimal and assume `userPath` is untrusted. Adapt the error handling to your application.

**Go 1.24 and later**: open files through [`os.Root`](https://pkg.go.dev/os#Root), which refuses any name that refers to a location outside the directory, including through `..` or symbolic links. It does not stop access to mount points, `/proc` files or devices inside the directory. For a purely lexical check of a relative path, use [`filepath.IsLocal`](https://pkg.go.dev/path/filepath#IsLocal).

```go
root, err := os.OpenRoot("/srv/uploads")
if err != nil {
    return err
}
defer root.Close()

f, err := root.Open(userPath) // fails if userPath escapes /srv/uploads
```

**Java**: `Path.startsWith` compares name elements, not characters ([Java `Path.startsWith`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Path.html#startsWith(java.nio.file.Path))).

```java
Path base = Path.of("/srv/uploads").toRealPath();
Path target = base.resolve(userPath).normalize();
if (!target.startsWith(base)) {
    throw new SecurityException("Invalid path");
}
```

**Python**: [`os.path.realpath`](https://docs.python.org/3/library/os.path.html#os.path.realpath) resolves symbolic links and [`os.path.commonpath`](https://docs.python.org/3/library/os.path.html#os.path.commonpath) compares whole path components.

```python
base = os.path.realpath("/srv/uploads")
target = os.path.realpath(os.path.join(base, user_path))
if os.path.commonpath([base, target]) != base:
    raise ValueError("Invalid path")
```

**.NET**: [`Path.GetFullPath(path, basePath)`](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.getfullpath#system-io-path-getfullpath(system-string-system-string)) resolves the input against a fixed base. Keep the trailing separator on the base for the prefix check, and use a case-insensitive comparison on Windows.

```csharp
string baseDir = Path.GetFullPath("/srv/uploads/");
string target = Path.GetFullPath(userPath, baseDir);
if (!target.StartsWith(baseDir, StringComparison.Ordinal))
{
    throw new UnauthorizedAccessException("Invalid path");
}
```

**Node.js**: check the result of [`path.relative`](https://nodejs.org/api/path.html#pathrelativefrom-to) instead of comparing string prefixes.

```javascript
const base = path.resolve('/srv/uploads');
const target = path.resolve(base, userPath);
const rel = path.relative(base, target);
if (rel === '' || rel === '..' || rel.startsWith('..' + path.sep) || path.isAbsolute(rel)) {
  throw new Error('Invalid path');
}
```

The Java, .NET and Node.js examples check the path lexically, so a symbolic link inside the base directory can still point outside it. See the next section.

## Symbolic Links and Race Conditions

A check on the path string doesn't account for symbolic links that exist, or are created, inside the base directory. Resolving links before the check helps, but leaves a time-of-check to time-of-use (TOCTOU) race: an attacker who can write to the directory can replace a component with a link after the check and before the file is opened ([Go blog: Traversal-resistant file APIs](https://go.dev/blog/osroot)).

- Don't let untrusted users create files or links in directories the application reads from or writes to by path.
- Prefer APIs that enforce the restriction while opening the file, such as Go's `os.Root` or Linux [`openat2` with `RESOLVE_BENEATH`](https://man7.org/linux/man-pages/man2/openat2.2.html) (Linux 5.6 and later), which fails if any part of the resolution leaves the directory.
- Run the application with the least file system permissions it needs, so a traversal reaches as little as possible.

## Archive Extraction

Archive entries are filenames chosen by whoever built the archive. Extracting an entry named `../../app/config.yml`, or an absolute path, writes outside the destination directory, a problem known as [Zip Slip](https://github.com/snyk/zip-slip-vulnerability). Archives can also contain symbolic links or hard links that point outside the destination, which later entries are then written through.

- Validate every entry name with the containment check above before writing it, and reject the archive if any entry fails.
- Reject or skip symbolic link and hard link entries unless the application needs them.
- Use the library's safe extraction mode where one exists. Python's `tarfile` extraction filters do this, and the `data` filter is the default from Python 3.14. Pass `filter='data'` explicitly on older versions ([Python tarfile extraction filters](https://docs.python.org/3/library/tarfile.html#extraction-filters)).

## Windows Paths

Windows accepts path forms that checks written for Unix often miss ([Microsoft: Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)):

- Both `\` and `/` are separators, and paths starting with a drive letter (`C:\`) or a UNC prefix (`\\server\share\`) are absolute.
- Reserved device names such as `CON`, `NUL`, `COM1` and `LPT1` refer to devices, even with an extension like `NUL.txt`.
- Filenames that end with a space or a period aren't supported by Windows tools, so reject them.
- On NTFS, `file.txt::$DATA` is another name for `file.txt` and `file.txt:name` refers to a named stream of it, so a check on the name or extension can see a different string than the file that gets opened. Reject `:` in filenames ([Microsoft: File Streams](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams)).
- Names are case-insensitive by default, so compare them case-insensitively.

Use the platform's path functions for these cases instead of parsing paths yourself.

## File Inclusion

Passing user input to `include`, `require`, template loaders or similar functions lets an attacker load an unintended file and, depending on the language, run it as code. Map the input to a fixed allowlist of templates or modules instead of using it as a path. In PHP, [`open_basedir`](https://www.php.net/manual/en/ini.core.php#ini.open-basedir) limits which directory trees `include` and `fopen()` can access, which is a useful extra layer but not a replacement for not using the input as a path.
